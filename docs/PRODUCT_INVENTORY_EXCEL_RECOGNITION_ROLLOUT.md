# التشغيل المرحلي للتعرّف التلقائي على ملفات أجهزة 5G

## النطاق

هذه الخطة تغطي رفع `XLSX` أو `CSV` بدل كتابة خريطة أعمدة `JSON`، واعتماد قالب تعرّف بواسطة مدير المالية، ثم استخدام التعرّف نفسه أثناء إنشاء سند استلام الأجهزة.

النظام يقرأ جميع أوراق العمل، يحدد ورقة الأجهزة وصف العناوين، ويربط العناوين العربية والإنجليزية بالحقول القياسية. كما يدعم:

- جهاز واحد في كل صف.
- صف منتج تتبعه صفوف سيريالات مع توريث بيانات المنتج والأسعار.
- أكثر من عمود سيريال في الصف مع إنشاء جهاز مستقل لكل سيريال.
- مطابقة SKU أو الباركود أو الاسم أو alias مع كتالوج المورد المحدد.
- بصمة SHA-256 للتخطيط؛ لا يُعاد استخدام قالب معتمد إلا إذا تطابقت البصمة والمورد.

## الترتيب الإلزامي للنشر

1. أخذ نسخة احتياطية من قاعدة البيانات والتأكد من نجاح آخر backup restore drill.
2. نشر migrations بالترتيب `v148` ثم `v149` ثم `v150` ثم `v151`.
3. تشغيل:

   ```bash
   npm run db:verify-migrations
   npm run test:db
   npm run verify:product-inventory
   npm run typecheck
   npm run lint:strict
   npm run test:unit
   npm run build
   ```

4. نشر التطبيق بعد نجاح migrations، لأن API يعتمد على أعمدة ومهام `v148–v151`.
5. التأكد أن cron الخاص بحذف الملفات المؤقتة يعمل؛ نفس worker ينهي التحليلات غير المعتمدة بعد سبعة أيام ويطلق ملفاتها للحذف الآمن.

## UAT المطلوب

ينفذ مدير المالية الحالات التالية على مورد تجريبي، مع مقارنة عدد السيريالات في الملف بعدد الصفوف المعروضة:

| الحالة | النتيجة المطلوبة |
|---|---|
| ملف عربي وصف العناوين بعد عنوان وتفاصيل المورد | اكتشاف الشيت وصف العناوين والأعمدة الأساسية |
| ملف إنجليزي بالعناوين القياسية | اعتماد تلقائي بدون تعديل |
| شيت Summary وشيت Devices | اختيار Devices وعدم استيراد Summary |
| منتج واحد ثم صفوف سيريالات فارغة المنتج والسعر | توريث القيم وإنشاء جهاز لكل سيريال |
| Serial 1 وSerial 2 في نفس الصف | إنشاء جهازين مع نفس بيانات المنتج التجارية |
| سيريال رقمي قد يفقد leading zero | إيقاف الصف وطلب تنسيق السيريال كنص |
| سيريال مكرر داخل الملف أو المخزون | منع الاعتماد وإظهار التكرار |
| SKU غير موجود لدى المورد المحدد | إظهار الصف كغير مطابق وطلب اختيار المنتج |
| تغيير اسم/ترتيب الأعمدة بعد اعتماد قالب | بصمة جديدة؛ لا يستخدم النظام القالب القديم بصمت |
| ملف ناقص التكلفة أو سعر البيع | رفض التحليل الآلي وتوجيه المالية لمراجعة القالب |

لا يتم توقيع UAT إلا بعد نجاح كل الحالات وعدم وجود فرق بين السيريالات المصدر والصفوف الناتجة.

## التشغيل التدريجي

1. ابدأ بمنشأة تجريبية ومورد واحد وملفين معروفين.
2. راقب `/api/internal/product-inventory` بعد كل دفعة. الاستجابة يجب أن تكون `200` و`status: ok`.
3. راجع القسم `workbook_recognition`، خصوصًا:

   - `stale`: تحليل ظل عالقًا أكثر من 15 دقيقة.
   - `failed_last_24_hours`: فشل تحليل حديث.
   - `low_confidence_last_24_hours`: ملفات احتاجت مراجعة قوية.
   - `overdue_sample_cleanup`: ملفات عينات تجاوزت مدة الاحتفاظ ولم تُحذف.

4. وسّع التشغيل إلى المورد التالي فقط بعد يوم عمل دون فروق في الأعداد أو الأسعار.
5. احتفظ بعينة معتمدة لكل تخطيط متكرر؛ التطابق اللاحق يتم بالبصمة وليس باسم الملف.

## الإيقاف والـ rollback الآمن

عند ظهور فرق في عدد الأجهزة أو اختيار أعمدة خاطئ، لا تحذف migrations ولا تعدل سجل التحليل:

```sql
UPDATE public.product_inventory_commerce_settings
SET automatic_workbook_recognition_enabled = false
WHERE organization_id = '<organization-id>'::uuid;
```

هذا يوقف تحليل القوالب واستيراد Excel/CSV لهذه المنشأة فقط، مع بقاء الاستلام اليدوي والاستلام بالصور متاحين. السندات المؤكدة لا تتغير.

بعد إصلاح السبب واختبار نفس الملف في UAT، أعد التفعيل:

```sql
UPDATE public.product_inventory_commerce_settings
SET automatic_workbook_recognition_enabled = true
WHERE organization_id = '<organization-id>'::uuid;
```

إذا أنشأ الملف سندًا في حالة `needs_review` ولم يُعتمد، ألغِ السند من التدفق المعتاد وارفع الملف بعد الإصلاح. لا تعدل `mapping_snapshot` أو `layout_fingerprint` يدويًا؛ هما دليل تدقيق لما استخدمه النظام فعليًا.

## التوقيع

- مدير المالية: صحة التكلفة وسعر البيع والعمولة والعملة.
- مدير المشروع: صحة المورد/المشروع وعدد الأجهزة المتوقع.
- مسؤول النظام: نجاح المراقبة والاحتفاظ والنسخ الاحتياطي.
- قرار الإطلاق: `GO` أو `NO-GO` مع التاريخ وأسماء ملفات UAT وبصماتها.
